# Manual test — M0.3 App shell (window, docks, command palette, keymap, theme, canvas)

Build: 5c7ff01   Tester:   Date:   Display server: Wayland / X11

This milestone is the first real `eda-ui`/`eda-app` behaviour (not a
throwaway spike): one Slint window with a left dock placeholder, a
wgpu-backed canvas `Image`, a status bar, a command palette overlay, a
keymap file, and theme tokens for the shell's own chrome. None of it has
been visually verified yet — the automated build in this repo's Nix
sandbox has no GPU/display, the same limitation `docs/manual-tests/M0.2.md`
records for the toolkit spikes. `nix flake check` passing for this
milestone proves the workspace builds, clippy/fmt are clean, and the
display-independent unit tests in `keymap.rs`/`app.rs`/`builtins.rs` pass
— it proves nothing about what actually renders or how input behaves. That
is what this checklist is for.

You do not need a PDK or xschem/ngspice/netgen for this milestone. You do
need a real GPU and a Wayland or X11 session — this cannot be checked
inside the Nix build sandbox.

## Before you start

- The left dock panel's label, the palette's exact command list, and the
  keymap bindings below are all read directly from the source shipped this
  session: `crates/eda-ui/ui/app.slint` (dock label "Library"),
  `crates/eda-cmd/src/builtins.rs` (the four builtin commands and
  `HELLO_MESSAGE`), and `crates/eda-ui/keymap/xschem.keymap` /
  `virtuoso.keymap` (the two shipped presets). If the running build's
  behaviour disagrees with what is written here, that is itself a bug to
  report (see "Reporting a failure" below) — the doc may be stale, not the
  app.
- **Known open item**: no Slint API was found to request a floating
  window on Wayland tiling compositors (the same caveat ADR-001 recorded
  for the M0.2 spikes). On a tiling compositor (e.g. Hyprland) the window
  may come up tiled small rather than at the requested 1600x1000 logical
  size — that is expected, not a bug. Whatever size it gets, the canvas
  should still show the correct themed clear color (step 5 below).
- **Known gap**: there is no runtime keymap-preset switcher yet. `App::new`
  (`crates/eda-ui/src/app.rs`) hard-codes the xschem-style preset
  (`XSCHEM_PRESET`) via `App::with_keymap(XSCHEM_PRESET)`. The
  Virtuoso-style preset (`VIRTUOSO_PRESET`) ships as data in the same
  binary but nothing in the shipped UI lets a human switch to it at
  runtime. Section 5 below covers how to check it anyway (it requires
  rebuilding with a one-line code change, not a UI toggle — there is no UI
  toggle to invent).

## 3. Theme toggle (and its undo/redo)

| # | Steps | Expected | Pass/Fail | Notes / screenshot |
| --- | --- | --- | --- | --- |
| 12 | With the palette closed, press `Ctrl+T` | The shell's **chrome** visibly recolors: dock background/border, status bar background, and window background flip from the dark token set to the light one (`crates/eda-ui/ui/theme.slint`: e.g. dock background `#2a2a30` -> `#e6e6ea`). The canvas's own clear color also flips (white <-> dark), since `Theme::toggled()` drives both | | |
| 13 | Press `Ctrl+T` again (or run `view.toggle_theme` from the palette) | Flips back to the previous theme | | |
| 14 | After a theme toggle, press `Ctrl+Z` | Theme flips back to what it was *before* that toggle (this is `edit.undo` driven through the same undo stack as any other command) | | |
| 15 | Press `Ctrl+Shift+Z` | Theme flips forward again (redo) — and specifically re-applies the toggle's recorded target, not a second blind toggle (this distinction matters: toggling twice from the same state is a no-op, so this step only proves correctness if step 14 undid an *odd* number of toggles first) | | |

## Reporting a failure
File used, exact steps, expected, actual, screenshot. Ask Claude Code for a
failing automated test first, then the fix. For this milestone "automated
test" mostly means `cargo nextest run` (the display-independent parts:
`crates/eda-ui/src/keymap.rs`, `crates/eda-ui/src/app.rs`'s helper
functions, `crates/eda-cmd/src/builtins.rs`) plus `crates/eda-ui/fuzz`'s
`keymap` fuzz target for parser-crash hunting — none of these can exercise
the actual windowed behaviour this checklist covers, since the Nix sandbox
has no GPU/display.
