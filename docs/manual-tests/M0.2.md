# Manual test — M0.2 UI spike (GPUI, egui, iced, Slint+canvas-wgpu)

Build: 74830ac   Tester:   Date:   Display server: Wayland / X11

This milestone has no `eda-ui`/`eda-app` behaviour to click through — it is
four **throwaway** spike binaries under `spikes/` (outside the Cargo
workspace) that each draw the same heavy scene (200k rects, 50k segments, 5k
labels, scale 1) or 4x that (scale 4) with pan/zoom, so `docs/adr/001-ui-toolkit.md`
can pick a toolkit on measurements. `spikes/` is deleted once that ADR is
accepted; until then this checklist is how a human confirms the windowed
behaviour the automated `nix flake check` build-only checks cannot (the Nix
sandbox has no GPU/display).

You do not need a PDK or xschem/ngspice/netgen for this milestone. You do
need a real GPU and a Wayland or X11 session — this cannot be checked inside
the Nix build sandbox.

## Before you start: the real results are surprising

`spikes/results/*.json` (committed, this build) already contains real
benchmark numbers from this machine (Intel Arc Graphics ARL iGPU, NixOS,
Wayland, `spikes` commit `8bb87d3`). Read these before testing so a slow or
crashing spike does not look like something you broke:

| Toolkit | scale 1 p95 frame_ms | scale 1 fps | scale 4 | Viable (p95 ≤ 16.7ms @ scale 1)? |
| --- | --- | --- | --- | --- |
| slint (shell) + canvas-wgpu | 5.33 | 227 | p95 30.1ms, fps 50 — **comfortable** | **Yes — only one that meets the bar** |
| gpui | 1408.5 | 1.9 | **crashes** (SIGKILL by Wayland compositor's "not responding" watchdog) | No — drastically slower than expected |
| egui | 205.1 | 8.2 | **crashes** (wgpu validation error: vertex buffer 308MB > 256MB device limit) | No |
| iced | 85.6 | 16.6 | runs, but p95 396.8ms, fps 3.4 | No (mediocre at scale 1, fails the scale-4 "comfortable" bar) |

Important nuance: the `slint` row is **not** Slint's own widgets — Slint
could not draw 200k primitives natively (see ADR Context), so that spike is
really "Slint shell + our own `canvas-wgpu` wgpu renderer". It is the number
that matters for the "shell + wgpu canvas" fallback architecture named in
`docs/PLAN.md`, not a measurement of Slint's native drawing throughput.

None of this is a reason to skip the windowed checks below — the architect
(step 11) needs the by-eye correctness check regardless of which toolkit
wins, and gpui/egui's scale-4 crashes should be reproduced once, not assumed.

## Friction log — window-size sanity check (please pay attention here)

**Flag this explicitly when you run the above.** The committed bench JSONs
report inconsistent actual window sizes even though all four spikes request
the same logical `1600x1000`:

- `iced`: `viewport_px: [1600, 1000]` — matches the request.
- `egui`: `viewport_px: [383, 463]` — far smaller than requested.
- `gpui`: `viewport_px: [784, 711]` — smaller than requested.
- `slint`: `viewport_px: [388, 463]` — far smaller than requested.

This was measured during `--bench` runs, not interactive ones, so it may be
an artifact of how the window manager/compositor placed an unfocused or
newly-spawned bench window rather than a real sizing bug. **When you run
each spike interactively in step 3/7/11/15 above, check whether the window
actually opens at 1600x1000** (e.g. `wlr-randr`/compositor window info, or
just eyeball it against your screen resolution) and record what you see per
spike in the Notes column. If egui/gpui/slint also come up undersized in
interactive mode, that is a real bug in how that spike requests its window
size (not a bench-only artifact) and should be reported to the architect
before ADR-001's Decision section is written — it would mean the frame-time
numbers for those three spikes were measured on a smaller/cheaper viewport
than iced's, which is not a fair comparison per the ADR's rule 4 (all
spikes requested the same window size identically).

## Reporting a failure

File used, exact steps, expected, actual, screenshot. Ask Claude Code for a
failing automated test first, then the fix. For this milestone "automated
test" mostly means `cargo nextest run` inside `spikes/scene` (the only crate
here with real unit tests) — a windowed-mode bug in one of the four spike
binaries themselves has no automated equivalent, since the Nix sandbox has
no GPU/display.

## Notes for the tester

- Each spike is its own Cargo package with its own `Cargo.lock`, not part of
  the root workspace — `cargo run` must be invoked from inside that spike's
  own directory (`spikes/spike-<name>/`), not the repo root.
- `--bench [--scale N] [--frames N] [--width N] [--height N]` runs the
  scripted 600-frame camera path non-interactively and prints one JSON
  report to stdout; this is what `bench.sh` drives. Running a spike without
  `--bench` is the interactive/windowed mode this checklist exercises.
- `canvas-wgpu` (the shared wgpu renderer used by the slint spike) has **no**
  automated test — it needs a real GPU device, which the Nix sandbox does
  not provide. Step 15-17 above (the slint spike) is the only place its
  correctness — rect fill, hairline segments, glyph atlas — is checked at
  all for this milestone.
- `nix flake check` passing for this milestone only proves the four spikes
  **compile** against the pinned `1.98.1` toolchain and the Nix-packaged
  system libraries. It proves nothing about frame times or correctness —
  that is what this whole document is for.
- gpui's present mode (vsync behaviour) is hard-coded by the platform layer:
  Mailbox (uncapped) on Wayland, Fifo (vsync-capped) on X11, with no public
  setter. If you test under X11, gpui's numbers/feel will differ from the
  Wayland results quoted above and that is expected, not a regression.
